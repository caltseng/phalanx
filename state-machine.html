Phalanx state machine

One registered writer stays with an item across separately fenced stage attempts. The server owns transitions; GitHub owns PR facts and merging. Authoritative transition rules.

Direct lifecycle

Publication and delivery

Publish one primary PR with an explicit target base. Ready-only work is never merged by its writer. Checked-in work may enable GitHub auto-merge, under repository rules. Trusted local checks are flags, not a Phalanx gate.

Draft publication is a ceiling: never promote or merge. Verify the open draft at the self-reviewed head, item branch and target base; a changed head returns to review. Draft completion satisfies no ready/check-in dependency.

A verified merge by anyone, via merge, squash or rebase, into the target completes either PR target. Failed checks, feedback and conflicts remain actionable writer flags. Closed without merge asks for input; never silently replace the PR.

Interruption and cancellation

Writer credentials have no timed expiry. Discover an uncertain launch by nonce. Replacement must name the current writer and attest its exact native session stopped after preserving local work and accounting for effects. Revoke the old token atomically.

Cancellation stops new work and reconciles in-flight effects before finalization. A verified merge wins over an attempted cancellation. Storage failure leaves a visible, retryable finalization, not a terminal execution without output.

Remaining runner stages: removal in PH-DS5 part 2

The retained PR creation, validation, promotion, review, revision and check-in stage implementations have no CLI scheduler or queue claim endpoint. Direct writers do not enter them. Their temporary observation/lease contracts and local SQLite stores remain until part 2; see the transition source.

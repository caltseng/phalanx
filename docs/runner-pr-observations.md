# Runner PR observations

Submit `POST /v1/items/{item_id}/executions/{execution_id}/pr-observation` with the runner bearer token and the current claim's `Phalanx-Lease`. Use an `Idempotency-Key` and repeat the same body and lease after an uncertain API response. Successful submissions return the updated execution. They record the observation in the timeline and end the attempt in the same transaction.

The runner credential authorizes the caller to attest facts from its GitHub adapter and repository policy. Keep that credential and the lease in the runner. Populate this route from exact GitHub reads and the runner's own expected refs, policy, and revision evidence. The worker result route remains the path for local stage results.

## Common fields

| Field | Value |
| --- | --- |
| `attempt_id`, `expected_version`, `stage` | From the current assignment. |
| `expected` | `head_ref` from the publication intent, `base_ref` from the work item or provider-resolved default, and `base_sha` for the exact target tip being evaluated. |
| `pull` | Exact read-back fields `number`, `head_repository`, `base_repository`, `head_ref`, `base_ref`, `head_sha`, `base_sha`, `state`, `draft`, and `merged`. Repository names use `owner/name`. Commit SHAs use 40 lowercase hexadecimal characters. |

The server checks the registered github.com remote, same-repository head and base, deterministic item branch, explicit target branch when supplied, expected refs, base tip, and assigned candidate SHA. Later observations also retain the primary PR's published base ref, including when intake used the default branch. It constructs the canonical PR URL from the registered repository and observed number. Subsequent successful submissions require the recorded primary PR.

## Stage fields

- `pr_creation` accepts an open, unmerged draft and optional `duplicate_numbers` from publication reconciliation. The runner verifies that duplicates match the publication intent. A successful observation records the primary PR and queues self-review.
- `pr_promotion` supplies `gates` with phase `draft`. Collect applicable draft evidence before requesting ready status. To advance, submit a read-back of the ready PR at that same revision. Failed draft checks can be submitted while the PR is still draft.
- `pr_validation` supplies `gates` with phase `ready`, covering applicable CI and preview checks. Passing advances to independent review, or back to reconciliation when the latest recorded review matches the exact PR, refs, head, and base. Failed checks schedule reconciliation.

- `adversarial_review` supplies `review` with a reviewer identifier, summary, and a list of findings (empty if there were none). Include severity in each finding. The runner verifies that an independent reviewer inspected the diff assigned by the passing PR gates. The server matches the review to that assignment and records it before queuing reconciliation.
- `pr_reconciliation` and `ready_for_check_in` each supply fresh `gates` with phase `ready`, plus `actionable_feedback_cleared: true` and `approvals_and_mergeability: true`. The runner attests that it resolved any actionable review findings and GitHub feedback, verified applicable repository approvals, and confirmed mergeability for the PR revision in the request. Reconciliation sends a missing or stale independent review back to review. If the ready revision or review has changed, the ready stage returns to reconciliation.
- A current `ready_for_check_in` observation finishes a ready-only target with the verified primary PR and its pinned revision. For a merge target, include `merge_intent` with a unique `operation_id` and the `authorization` basis. The runner verifies current authorization under the item and repository policy. The server records the intent in the execution timeline and queues a separate check-in attempt. The runner can read that timeline to recover the assigned revision and intent. Omit the intent on stale observations and ready-only targets.
- `check_in` supplies the same `operation_id`, the ordered `merge_parent_shas` from GitHub for `pull.merge_commit`, and an exact read-back of the closed, non-draft, merged primary PR with `pull.merge_commit`. Keep `expected.base_sha` at the pre-merge tip in the recorded intent. Use the actual provider read-back for `pull.base_sha`, which can differ after the merge. This v1 path requires a direct merge commit with exactly two parents, in order: the authorized pre-merge base, then the candidate head. The finalized output records the pre-merge revision and provider merge commit.

Before any merge write, the runner must persist its local operation journal under that operation ID and verify current claim authority, item and repository authorization, PR identity, head, base, latest approvals, feedback, checks, and merge policy again. Record the pre-merge observation and provider correlation in that journal. Obtain the ordered parent SHAs from the check-in coordinator's GitHub commit lookup (`get_commit_parents`, added in PR #29). The runner relays the provider's values under its own claim. Submit the verified merge only when GitHub evidence connects the resulting commit to the authorized revision and journaled write. A merged flag alone cannot establish that correlation. If a response is lost, reconcile the provider state and journal before retrying or submitting. If the head, base, merge commit, or operation cannot be attributed unambiguously, keep the write unresolved and surface the blocker. This route records evidence and does not write to GitHub.

The `gates` object carries `phase`, `number`, `head_sha`, `base_sha`, and an optional `test_merge_sha` verified by the runner to correspond to that head and base. Its `required` list describes applicable checks with `name`, `kind`, optional `app_id`, and optional `use_merge_sha` and `require_execution` booleans. Its `observations` list contains the latest normalized `name`, `kind`, `tested_sha`, `outcome`, and optional `app_id` per source. Kinds are `check_run`, `status`, and `preview`. Outcomes are `passed`, `pending`, `failed`, `neutral`, and `skipped`. Use an empty `required` list only after verifying the phase has no applicable requirements.

Malformed payloads return 422. Invalid claims, mismatched revisions, and unresolved gates return 409 without advancing the item. The runner still needs scheduled rechecks for pending gates, a path for conflict and feedback fixes that change the candidate, and recovery of ambiguous writes. A confirmed merge may finish a pending cancellation or failure disposition under the current attempt and version. The server records the terminal PR output, releases the claim, and stores the replay receipt in the same transaction.

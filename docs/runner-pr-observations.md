# Runner PR observations

Submit `POST /v1/items/{item_id}/executions/{execution_id}/pr-observation` with the runner bearer token and the current claim's `Phalanx-Lease`. Use an `Idempotency-Key` and repeat the same body and lease after an uncertain API response. Successful submissions return the updated execution. They record the observation in the timeline and end the attempt in the same transaction.

The runner credential authorizes the caller to attest facts from its GitHub adapter and repository policy. Keep that credential and the lease in the runner. Populate this route from exact GitHub reads and the runner's own expected refs, policy, and revision evidence. The worker result route remains the path for local stage results.

## Common fields

| Field | Value |
| --- | --- |
| `attempt_id`, `expected_version`, `stage` | From the current assignment. |
| `expected` | `head_ref` from the publication intent, `base_ref` from the work item or provider-resolved default, and `base_sha` for the exact target tip being evaluated. |
| `pull` | Exact read-back fields `number`, `head_repository`, `base_repository`, `head_ref`, `base_ref`, `head_sha`, `base_sha`, `state`, `draft`, and `merged`. Repository names use `owner/name`. Commit SHAs use 40 lowercase hexadecimal characters. |

The server checks the registered github.com remote, same-repository head and base, deterministic item branch, explicit target branch when supplied, expected refs, base tip, and assigned candidate SHA. Later observations also retain the primary PR's published base ref, including when intake used the default branch. It constructs the canonical PR URL from the registered repository and observed number. Subsequent successful submissions require the recorded primary PR.

## Stage fields

- `pr_creation` accepts an open, unmerged draft and optional `duplicate_numbers` from publication reconciliation. The runner verifies that duplicates match the publication intent. A successful observation records the primary PR and queues self-review.
- Before a primary PR is recorded, `POST /v1/items/{item_id}/executions/{execution_id}/pr-publication-blocker` adopts an existing PR found on the item branch by draft publication. Send the common fields, a short `reason`, and its `pull`. A moved target branch doesn't block the first draft; the runner submits the draft's observed base in `expected.base_sha`. The server records the PR as primary. At the candidate head it queues self-review, a foreign head returns to development with findings to integrate its commits, and a closed PR asks the owner. Submit a matching open draft at the candidate, expected base ref and base SHA as a `pr_creation` observation instead. The runner seals the body and replays it with the same key and lease.
- `pr_promotion` supplies `gates` with phase `draft`. Collect applicable draft evidence before requesting ready status. To advance, submit a read-back of the ready PR at that same revision. Failed draft checks can be submitted while the PR is still draft.
- `pr_validation` supplies `gates` with phase `ready`, covering applicable CI and preview checks. The results, including failures, always advance to reconciliation.
- The published-validation runner first calls `POST /v1/items/{item_id}/executions/{execution_id}/pr-validation-claim` with the assignment, `runner_id`, and lease. The response identifies the ready primary PR recorded at promotion. The runner verifies the candidate and published target branch, then collects evidence against the current verified target tip.
- With `schedule_recheck: true` on a `pr_validation` observation, pending or missing gates release the claim and schedule a PH-08 recheck for that exact revision. After five scheduled rechecks on the same revision, the next pending observation requests an owner reply. Unverified policy and inaccessible evidence request an owner reply through the result route. The runner seals each outcome locally and replays the same body, lease, and idempotency key after an uncertain response.
- Transient GitHub read failures use the bounded dispatch retry budget. The runner submits a failed result with a technical reason and a `retry_after_seconds` delay. The server respects that minimum and its own backoff before dispatching the next attempt.

- `adversarial_review` supplies `review` with a reviewer identifier, summary, and a list of findings (empty if there were none). Include severity in each finding. The runner verifies that an independent reviewer inspected the diff assigned by the passing PR gates. The server matches the review to that assignment. The default `outcome` is `succeeded`, which records the review for the current revision and queues reconciliation. `outcome: "changes_required"` needs at least one finding; it records the findings without counting them as a current review and queues `pr_revision`, which receives them in its packet context as `review_findings`. The review context carries `since_head`, the head of the last successful review on the PR, so the reviewer covers only the diff since then.
- `pr_reconciliation` supplies fresh `gates` with phase `ready` for the current head. The runner submits only after confirming mergeability and that no actionable GitHub feedback is new; it sends conflicts and new feedback through `pr-rework` instead. Failed checks go to `pr_revision` with the failed gate reasons as findings. A head without a successful independent review goes to review; the review is keyed on the head, so a base-only change reuses it.
- `pr_revision` submits the pushed revision with `candidate`, the new commit, and a read-back of the open, ready PR. The server requires a new candidate and a PR head that has moved off the old one. A PR head at the candidate queues `pr_validation`. A push that lost to a foreign one still records the candidate, and reconciliation sends the foreign head back to revision. A closed PR asks the owner. A revision that turns into new scope submits `changes_required` through the result route with `review_notes` and the old candidate, which returns the item to development.
- `POST /v1/items/{item_id}/executions/{execution_id}/pr-rework` sends routine PR state to `pr_revision` from `pr_reconciliation` or `check_in`, and back to development from `pr_promotion`, before the PR was first marked ready. At `pr_validation` it returns to reconciliation. Send the common fields, the observed `expected` refs and `pull` of the open primary PR, and an `issue`: `merge_conflict` (GitHub reports the candidate unmergeable) with `base_tip`, the target branch tip the runner just read, since GitHub doesn't advance the PR's `base.sha` when the branch moves, `unexpected_head` (the PR head is not the candidate and cannot be fast-forwarded to it), or `feedback` with matching `findings` and `feedback_ids` lists. Feedback covers requested-changes reviews and unresolved, non-outdated review threads; the runner skips IDs already in the execution timeline, so each item is handed off once. The server writes integration findings for the first two issues. After ten such revision rounds, or a third round with identical findings, since the last owner reply, the server asks the owner instead.
- A `pr_reconciliation` observation with every gate current, including a review of the current head, finishes a ready-only target with the verified primary PR and its pinned revision. For a `checked_in` target, include `merge_intent` with a unique `operation_id` and the `authorization` basis when the runner's `auto_merge` setting is on (the default). Merge authorization comes from the target and repository policy: GitHub's required reviews, checks and rulesets gate the merge, and Phalanx adds no gate. The server records the intent in the execution timeline before it queues a separate check-in attempt, so the intent is durable before any provider call. The runner reads that timeline to recover the assigned revision and intent. Without an intent, a merge target completes with the ready PR and the owner merges. Omit the intent on failed observations and ready-only targets; the server rejects an intent for a ready-only target and uses it only once every gate is current.
- `check_in` supplies the same `operation_id`, the ordered `merge_parent_shas` from GitHub for `pull.merge_commit`, and an exact read-back of the closed, non-draft, merged primary PR with `pull.merge_commit`. Keep `expected.base_sha` at the pre-merge tip in the recorded intent. Use the actual provider read-back for `pull.base_sha`, which can differ after the merge. This v1 path requires a direct merge commit with exactly two parents whose second (head) parent is the candidate head. The first parent may differ from the authorized base when the base advanced before the merge. The finalized output records the pre-merge revision and provider merge commit.

Every check-in attempt reconciles first: it reads the PR and, if GitHub reports it merged, verifies the merge commit's parents and submits the verified merge without writing. Otherwise the runner verifies its claim, PR identity, the ready head and mergeability, then requests a direct merge commit with GitHub's `sha` head precondition. A lost or ambiguous response, a timeout, a rate limit or a 409 retries with backoff, and the next attempt reconciles before any new write. A conflict or unexpected head goes to `pr_revision` through `pr-rework` with stage `check_in`. A 405 from GitHub (the repository's rules block the merge, or its settings disallow merge commits) waits as external gate `merge` and then asks the owner; an owner's manual merge is adopted on the next attempt if the head parent matches. If the PR, head or merge commit cannot be attributed unambiguously, the runner asks the owner. A merged flag alone never completes the item. This route records evidence and does not write to GitHub.

After an item completes with a ready PR and no merge, `GET /v1/runner/owner-merge-watches?limit=50` lists it while a queued dependent waits on it at milestone `checked_in`. Each entry gives `item_id`, `execution_id`, `repository_id`, `remote`, `target_branch`, `head_ref`, `pr_url`, and the verified `revision`. When GitHub shows the PR merged by any method with its head at `revision.head`, post `POST /v1/items/{item_id}/executions/{execution_id}/owner-merge` with `runner_id` and the merged `pull` read-back, including `pull.merge_commit`, under an idempotency key. The server accepts only the latest completed execution's unmerged primary PR at that head. It records the merge once, rejects a different merge commit, and leaves the closed execution unchanged. Dependents then pin the merge commit.

The `gates` object carries `phase`, `number`, `head_sha`, `base_sha`, and an optional `test_merge_sha` verified by the runner to correspond to that head and base. Its `required` list describes applicable checks with `name`, `kind`, optional `app_id`, and optional `use_merge_sha` and `require_execution` booleans. Its `observations` list contains the latest normalized `name`, `kind`, `tested_sha`, `outcome`, and optional `app_id` per source. Kinds are `check_run`, `status`, and `preview`. Outcomes are `passed`, `pending`, `failed`, `neutral`, and `skipped`. Use an empty `required` list only after verifying the phase has no applicable requirements.

Malformed payloads return 422. Invalid claims, mismatched revisions, and unresolved gates without a scheduled disposition return 409. The runner still needs recovery of ambiguous merge writes. A confirmed merge may finish a pending cancellation or failure disposition under the current attempt and version. The server records the terminal PR output, releases the claim, and stores the replay receipt in the same transaction.

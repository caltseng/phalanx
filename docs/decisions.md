# Phalanx decisions

These are design calls for Phalanx. Most are best guesses the Captain made without asking Caleb; Caleb reviews them and may override any one. The **Decided by** column separates the two:

- **Caleb**: Caleb made the call explicitly. Agents don't change it without asking him.
- **Captain**: an agent's best guess, open to Caleb's override.
- **Captain; confirmed, approved or amended by Caleb**: the agent proposed it and Caleb explicitly accepted or changed it.

Mark a row Caleb only for his explicit decision. To override, edit the row, set Decided by to Caleb and note the change. The Captain appends new decisions as it makes them. Worker questions it answers are also recorded on the item as `answered_by: captain`.

| 1 | Pilot (pilot-web#1) | titleCase preserves runs of whitespace and capitalizes only non-empty words | Fixes the crash without changing output spacing | Captain |
| 2 | Owner questions | The Captain answers all worker questions (`answered_by=captain`) and logs them here | Caleb asked not to be blocked on these | Caleb |
| 3 | Validation | Pending draft and ready CI waits and rechecks every `check_recheck_seconds` (runner config, default 30s); it is not counted as a failure. Caleb asked for a configurable interval; the 2-hour default limit is a Captain decision | Caleb (configurable interval); Captain (2-hour default limit) |
| 4 | Validation | A transient git/network error during a PR update retries, and escalates only after 5 failures | Self-resolution | Captain |

| 6 | Validation | Phalanx never converts a PR back to draft once it is marked ready; only a human may. A ready PR missing draft-only evidence skips those checks, recorded as skipped on the PR, and continues. If a human converts the PR to draft, Phalanx leaves it draft and asks the owner before marking it ready again. No auto-waiver of required CI | Draft-only checks can't run on a ready PR, and reverting to draft is the human's call | Caleb |
| 7 | Publication | A rebased candidate force-replaces the PR head only if that head is the one Phalanx last verified; otherwise it asks | Never overwrite someone else's push. | Captain; confirmed by Caleb |
| 8 | Review | Independent review "changes required" goes back to development with the findings | Same loop as self-review | Captain |
| 9 | Check-in | Ready-only items complete automatically; merge targets wait on the owner until PH-15a part 3 | Automated merge isn't built yet | Captain |
| 10 | Check-in | Merge conflicts are resolved automatically by a development attempt that rebases and revalidates; the owner is asked only when retries can't make progress. | Caleb asked for automatic conflict resolution | Caleb |
| 11 | Architecture | The server needs the `[server]` extra (fastapi/uvicorn); backup/restore are server-host-only commands. Runners, the CLI and the Captain reach queue state only through the API, even when the server runs locally; their own SQLite files are runner-local journals | Runners stay light and can't touch server storage; the API is the only path once storage is hosted | Captain; confirmed by Caleb |
| 12 | Architecture | The dashboard is served from the API server's origin; a separate static origin is deferred | No CORS or extra config needed | Captain |
| 13 | Language | Stay on Python for v1; port to TypeScript/Node after PH-V1 and before hosting (PH-25) | Don't delay v1; host once | Captain; approved by Caleb |
| 14 | Process | Feature PRs edit only their own plan row; plan and muster PRs own ordering and statuses | Stops rebase churn. Superseded by 19 | Captain |
| 15 | Worker questions | Options must be separate list items; an unambiguous combined string is split rather than rejected (PH-11g) | Lenient over strict | Captain |
| 16 | Worker questions | An options string that can't be split unambiguously is kept as one option instead of rejected; a single option is allowed (PH-11g follow-up) | A malformed option list shouldn't stall the item | Captain |
| 17 | Publication | When a stage returns the item to development with findings or records a permitted pre-validation bypass, the runner posts one PR comment (keyed on revision and findings, so retries don't duplicate) and keeps a "Known gaps" section in the PR description, removed once a later revision clears it. Writes go through a runner-local outbox, retry up to 5 times and never block the item | Caleb wants deficiencies noted on the draft PR rather than hidden in the queue | Caleb |
| 18 | Publication | The draft PR opens as soon as development delivers a verified candidate. Only push safety (candidate verified on the base, claim current, no outside push to the item branch), duplicate-PR lookup and a deleted target branch can stop it. A moved target branch no longer sends the item back to development; later stages validate against the current base, and deficiencies go into Known gaps | Caleb: "The barrier to create draft PRs should be fairly low" | Caleb |
| 19 | Process | Feature PRs don't edit IMPLEMENTATION_PLAN.md; the Captain batches status updates after merges. Approved PRs use GitHub auto-merge pinned to the reviewed head | Plan conflicts forced rebases and CI reruns; auto-merge removes a round trip | Captain; approved by Caleb |
| 20 | Check-in | Merge conflicts, unexpected PR heads, failed checks and actionable GitHub feedback at any published PR stage return to development as findings and are revalidated. The owner is asked after 10 such rounds, or a third round with identical findings, since the last owner reply (PH-15a part 2) | Self-resolution with a bounded escalation; failed-check findings omit the head SHA so repeats are detectable | Captain |
| 21 | Check-in | Actionable feedback means requested-changes reviews and unresolved, non-outdated review threads; each is handed off once by GitHub node ID. Once handed off, a thread no longer blocks Phalanx's own attestation even if it stays unresolved; GitHub's review and conversation-resolution rules still gate the merge. Plain PR conversation comments are not treated as actionable (PH-15a part 2) | Avoids re-sending the same comment every round and treating chatter as blockers | Captain; confirmed by Caleb |
| 22 | Publication | A PR head that Phalanx did not verify is only fast-forwarded to the candidate, never force-overwritten; if that fails, development integrates the foreign commits (PH-15a part 2) | Never discard someone else's push | Captain; confirmed by Caleb |
| 23 | Check-in | Merge targets merge automatically once GitHub's required reviews and checks pass on the verified head. Auto-merge is a runner setting, on by default; when off, the PR is marked ready and the owner merges (PH-15a part 3). Supersedes row 9 when part 3 lands | Autonomy by default, with an opt-out | Caleb |
| 24 | State machine | Once a PR is first promoted to ready, it has its own revision loop: `pr_reconciliation` sends conflicts, failed checks, actionable feedback and blocking review findings to a `pr_revision` stage, which fixes them on the open PR, self-reviews only the new diff, reruns the failed checks plus the local checks covering the changed files, and pushes; `pr_validation` observes CI on the new head and the loop returns to reconciliation, where adversarial review covers only the diff since the last reviewed head. The PR never goes back to draft. Before first promotion, fixes stay in `development`, which keeps one meaning: building the candidate. A revision that turns into new scope escalates there. Built in PH-15b; amends row 20 | Post-PR fixes are an expected loop and should cost what they change, without blurring what development means | Caleb |
| 25 | State machine | In the revision loop, draft-only checks are recorded as skipped; they gate only the first promotion (see row 6). `ready_for_check_in` folds into `pr_reconciliation`, `pr_validation` always returns to reconciliation, and the moved-base publication route is pruned (PH-15b) | Follows from row 24 without reverting to draft; removes a duplicate stage and redundant edges | Captain |
| 26 | Check-in | The durable merge intent is the server-recorded `merge_intent` on the ready observation, written before `check_in` is queued. There is no runner-local merge journal; every check-in attempt reconciles from GitHub before any write (PH-15a part 3) | Reuses the timeline as the single source of truth | Captain |
| 27 | Check-in | Phalanx merges with a direct merge commit pinned by GitHub's expected-head precondition. A merge is verified when the PR is closed and merged and the merge commit's head (second) parent is the verified head, even if the base advanced (PH-15a part 3) | Base drift is harmless; head identity is what matters | Captain |
| 28 | Check-in | A merge GitHub refuses (HTTP 405) waits as external gate `merge`, then asks the owner. An owner's manual merge is adopted when its head parent matches. Timeouts, 409s, 429s, unknown mergeability and lost responses retry with backoff and reconcile first (PH-15a part 3) | GitHub's rules gate the merge; Phalanx adds none | Captain |
| 29 | Check-in | A conflict or unexpected head at `check_in` reuses the rework route and its no-progress cap; PH-15b moves it to `pr_revision` (PH-15a part 3) | No parallel loop | Captain |
| 30 | State machine | `pr_revision` is a worker stage. The runner pushes and verifies its commit on submit; if a foreign push wins the race, the candidate is still recorded and reconciliation sends the foreign head back to `pr_revision`. A revision that turns into new scope escalates to development as `changes_required` (PH-15b) | Keeps GitHub writes on the runner path and reuses existing routes instead of new states | Captain |
| 31 | State machine | Blocking adversarial-review findings go straight to `pr_revision`; a `changes_required` result at `pr_validation` returns to reconciliation, which reobserves the PR and routes what failed (PH-15b) | Same outcome as row 24 with fewer hops | Captain |
| 32 | State machine | Reconciliation observes CI and previews on the current head itself, so it never sends work back to `pr_validation`. It no longer attests approvals: GitHub's required approvals gate the merge at `check_in` (the 405 wait), and a ready-only or auto-merge-off item completes with the ready PR without waiting for approvals (PH-15b) | Avoids duplicating gates GitHub already enforces; the owner handles approval on a delivered PR | Captain; confirmed by Caleb |
| 33 | State machine | The independent review is keyed by head only, so a base-only change reuses it; this removes the moved-base route (PH-15b) | A base move alone does not change the reviewed diff | Captain |
| 34 | Publication | When an existing PR blocks the first draft, `pr_creation` adopts it: a candidate head continues to `self_review`, a foreign head returns to development with integration findings, and a closed PR asks the owner (PH-15b) | Deletes the `publication_conflict` hop | Captain |
| 35 | State machine | The no-progress cap (row 20) counts rounds into development or `pr_revision` from the PR stages, and a store migration moves in-flight `ready_for_check_in` rows and history to `pr_reconciliation` (PH-15b) | Keeps the bounded escalation and in-flight merge intents across the upgrade | Captain |
| 36 | Envelope probe | The load and fault probe lives in `tests/envelope_probe.py` as a rerunnable CLI, and CI runs a small configuration of it (PH-19a) | Rerunnable on every OS without new tooling | Captain |
| 37 | Envelope probe | The probe simulates lease expiry by moving lease deadlines in the store, a store outage with an external `BEGIN EXCLUSIVE`, and a crash by hard-killing the server and restarting on a new port (PH-19a) | Deterministic, portable and tests crash recovery rather than a graceful shutdown | Captain |
| 38 | Envelope probe | Any 500, or any connection failure outside a fault window, counts as a violation; readiness polls during boot are not recorded (PH-19a) | Never fail silently, without false alarms while the server starts | Captain |
| 39 | API errors | A busy or locked SQLite store returns 503 with `Retry-After: 1` on every route; other store errors stay 500 (PH-19a) | Clients retry contention safely through leases and idempotency keys, and permanent errors are not disguised as transient | Captain |
| 40 | Plan | The claim latency and recheck drain misses from PH-19a do not gate PH-V1; they move to PH-26 | They are documented degradations with a visible reason, and correctness, fairness and recovery targets were met | Captain |
| 41 | Storage | Read starvation under write load is fixed with a reader-priority gate in the server process, staying on DELETE journal mode rather than WAL (PH-19b) | WAL needs the WAL-reset check first, and `migrate()` and `snapshot()` assume DELETE mode; WAL and throughput stay in PH-26 | Captain |
| 42 | Storage | Waiting readers take their read lock, including the schema load in `connect`, before the next writer starts; a writer waits at most 2 s for readers and a reader at most 2 s for a writer, which then returns the existing 503. `/health` is not gated (PH-19b) | Neither side can starve the other, the retry contract is unchanged, and health still reports a store outage directly | Captain |
| 43 | Check-in | Phalanx always delivers the PR; whether it merges is set case by case, per item with the intake target (`ready_for_check_in` delivers the ready PR, `checked_in` merges it) and globally with the runner setting `auto_merge` (default on), which when off ends every item at the ready PR | Delivery is the guarantee, check-in is a per-case choice | Caleb |
| 44 | Auth | Google sign-in covers the owner's browser view of the dashboard only; runners, the CLI and the Captain keep bearer tokens (PH-27) | Interactive sign-in doesn't fit headless machines, and the dashboard is where pasting a token hurts | Captain |
| 45 | Auth | A Google session cookie authorizes only the read-only operator routes; owner writes such as intake and replies stay on the owner token (PH-27) | Safe-method-only cookies need no CSRF defense; phone intake (PH-21) can extend it when it needs writes | Captain |
| 46 | Auth | The ID token is accepted from Google's token endpoint over TLS after claim checks, without a JWT signature library; sessions are server-side rows with a hashed ID (PH-27) | The OIDC spec allows TLS validation for a direct token-endpoint response; store sessions can be revoked and move with the hosted store | Captain |
| 47 | Users | Phalanx will be used by people other than Caleb, so it is architected for many users | Caleb's direction for the product beyond his own use | Caleb |
| 48 | Users | A workspace is the tenancy boundary that scopes every server record. Users come from the sign-in provider's subject ID and have owner, member or viewer roles per workspace. People get personal API tokens and runners get per-runner tokens. Each user's runners keep their own Git credentials. v1 ships one implicit workspace, and PH-28 adds the rest | The smallest model that supports both solo users and teams on one hosted server without rework, and keeps the server free of Git credentials | Captain |
| 49 | Dashboard | [DASHBOARD.md](../DASHBOARD.md) is accepted as the hosted dashboard's goals and UI principles, delivered in phases D1 to D3 as PH-29 to PH-31 | Accepted in review of #112 | Caleb |
| 50 | Pilot report | For PH-V1 item `2abe1a14` (pilot-web input handling), recommendations prefer throwing `TypeError`/`RangeError` for invalid input, while empty and whitespace-variant strings stay valid and `titleCase` preserves whitespace | It matches `chunk`'s existing `RangeError` and keeps decision 1 for whitespace | Captain |
| 51 | Roadmap | Finish v1 and get it validated, polished and running smoothly before any hosting, multi-user or dashboard work; [ROADMAP.md](../ROADMAP.md) orders the stages and links each one to its specs. PH-27 is paused, with its branch kept | Caleb's direction after accepting the multi-user and dashboard specs | Caleb |
| 52 | GitHub intake (#116) | Import explicitly by registered repository ID and issue number with local GitHub credentials; snapshot the issue and all comments through existing owner API intake. Choose the target explicitly, reject oversized context instead of truncating, and use a stable issue key so changed retries conflict rather than duplicate work. Polling, webhooks and synchronization are deferred | Smallest complete ingestion path without server-held Git credentials, new lifecycle states or implicit dispatch/merge authority | Captain |
| 53 | Roadmap | v1 is declared polished when PH-V1b and PH-V1c (one clean batch of about five real items with zero manual steps or duplicate PRs) pass and `main` CI stays green. Only blocking findings are fixed before that. PH-26's measurement report is part of stage 2. Its code fix doesn't gate v1 and may still land if it stays simple and doesn't complicate the code | Bound the polish stage so it can't drag on, and value simplicity overall; throughput only matters at 10,000-item scale | Caleb |
| 54 | Validation retries (PH-V1d) | A development retry may return the recorded candidate unchanged, for example after a flaky local check, which reruns self-review and pre-PR validation. Self-review and pre-PR validation findings now count toward the existing rework cap (10 rounds, or a third with identical findings, between owner replies). A failed local check records the last 4 KB of its combined output | Lets spurious failures self-resolve without a new setting, bounds the loop with the existing cap, and gives the worker output to act on | Captain |
| 55 | Runner blockers (PH-V1e) | The runner sends a slot's current blocker as an optional `blocker` field on lease renewal, stored on the attempt; a renewal without it clears it. The operator summary shows it as the item's `wait_reason` only when the item has no other wait. Results that make no observation no longer replace a block | Makes runner-only waits visible through the existing lease call with no new lifecycle state | Captain |

# Phalanx decisions

These are design calls for Phalanx. Most are best guesses the Captain made without asking Caleb; Caleb reviews them and may override any one. The **Decided by** column separates the two:

- **Caleb**: Caleb made the call explicitly. Agents don't change it without asking him.
- **Captain**: an agent's best guess, open to Caleb's override.
- **Captain; confirmed, approved or amended by Caleb**: the agent proposed it and Caleb explicitly accepted or changed it.

Mark a row Caleb only for his explicit decision. To override, edit the row, set Decided by to Caleb and note the change. The Captain appends new decisions as it makes them. Worker questions it answers are also recorded on the item as `answered_by: captain`.

| 24 | State machine | Once a PR is first promoted to ready, it has its own revision loop: `pr_reconciliation` sends conflicts, failed checks, actionable feedback and blocking review findings to a `pr_revision` stage, which fixes them on the open PR, self-reviews only the new diff, reruns the failed checks plus the local checks covering the changed files, and pushes; `pr_validation` observes CI on the new head and the loop returns to reconciliation, where adversarial review covers only the diff since the last reviewed head. The PR never goes back to draft. Before first promotion, fixes stay in `development`, which keeps one meaning: building the candidate. A revision that turns into new scope escalates there. Built in PH-15b; amends row 20 | Post-PR fixes are an expected loop and should cost what they change, without blurring what development means | Caleb |
| 25 | State machine | In the revision loop, draft-only checks are recorded as skipped; they gate only the first promotion (see row 6). `ready_for_check_in` folds into `pr_reconciliation`, `pr_validation` always returns to reconciliation, and the moved-base publication route is pruned (PH-15b) | Follows from row 24 without reverting to draft; removes a duplicate stage and redundant edges | Captain |
| 26 | Check-in | The durable merge intent is the server-recorded `merge_intent` on the ready observation, written before `check_in` is queued. | 27 | Check-in | Phalanx merges with a direct merge commit pinned by GitHub's expected-head precondition. | 28 | Check-in | A merge GitHub refuses (HTTP 405) waits as external gate `merge`, then asks the owner. An owner's manual merge is adopted when its head parent matches. | 29 | Check-in | A conflict or unexpected head at `check_in` reuses the rework route and its no-progress cap; PH-15b moves it to `pr_revision` (PH-15a part 3) | No parallel loop | Captain |

| 31 | State machine | Blocking adversarial-review findings go straight to `pr_revision`; a `changes_required` result at `pr_validation` returns to reconciliation, which reobserves the PR and routes what failed (PH-15b) | Same outcome as row 24 with fewer hops | Captain |
| 32 | State machine | Reconciliation observes CI and previews on the current head itself, so it never sends work back to `pr_validation`. | 33 | State machine | The independent review is keyed by head only, so a base-only change reuses it; this removes the moved-base route (PH-15b) | A base move alone does not change the reviewed diff | Captain |

| 56 | Lease timing (PH-V1g) | Leases last 300 s by default, set on the server with `PHALANX_LEASE_SECONDS` (whole seconds, 30-3600; invalid values stop startup). | 58 | Dependencies | Items filed in a dependency chain target `checked_in`, so Phalanx merges each one after required CI and its own reviews. | 59 | Local board (PH-V1i) | With `PHALANX_LOCAL_BOARD=1`, the read-only board routes (`/v1/operator/*` and the stored report route) accept requests without a token when both the client address and the `Host` header are loopback (`localhost`, `127.0.0.1` or `[::1]`). The flag defaults off, so a hosted server stays closed. Every other route, and any request carrying a token, authenticates exactly as before. Hosted sign-in stays with PH-27 | "While the dashboard is local only, don't ask for a secret." Request facts alone can't tell local from hosted: a same-host reverse proxy or tunnel connects from loopback and may rewrite `Host` to the upstream address, so an opt-in flag is the simplest gate that never opens a hosted server by accident; the `Host` check blocks DNS rebinding | Caleb |
| 60 | Long-running workers (PH-V1k) | An attempt whose exact native writer is still active 3 h after launch, with no result, reports one `worker_overdue` loop status and publishes it as the slot blocker, so the board shows it as the item's `wait_reason`. The loop keeps renewing and never stops the worker. A writer observed stopped without a result stops renewing that lease, so the existing stopped-attempt recovery (retry with backoff, owner intervention after five) reconciles it instead of holding the item forever. The 3 h bound is a `CaptainLoop` default, not a new setting | A busy worker and a hung tool call look identical from native state, so surface age instead of guessing; generous to suit loaded machines (decision 56) | Captain |
| 61 | State machine (PH-V1j) | A merge conflict at any PR stage, including `pr_promotion` before the first promotion, goes to `pr_revision`, which resolves it on the open PR and reruns the relevant checks. A revised PR that is still a draft returns to `pr_promotion` for its draft-only checks. Failed draft-only checks and unexpected heads before the first promotion still return to `development`, and the rework cap (row 35) counts these rounds. Amends rows 10 and 24 for merge conflicts | "Merge conflicts should not send back to development. They should resolve as part of the post-pr cycle loop like the self-reviews." | Caleb |
| 62 | PR check evidence | Draft-only check evidence in `pr_promotion` binds to the PR's head and the base GitHub records for it (`base.sha`), not the live target tip, so an ordinary target advance doesn't block promotion; a new conflict takes the merge-conflict path. Ready evidence in `pr_validation` still binds to the live target tip, and a repo that requires an up-to-date branch enforces it through GitHub's rules at `check_in` (a refused merge waits, then asks the owner). A head change, retarget, closed or merged PR still stops promotion | GitHub doesn't advance `base.sha` when the target moves, so requiring the tip to match it looped every queued draft (#138, #145) on 30 s retries after any merge to `main`, and their failed draft checks were never seen. GitHub's mergeability and branch rules already own current-base compatibility | Captain |
| 63 | Dispatch (stage continuation) | Keep working until you really can't anymore. An admitted item keeps its runner's capacity reservation across immediately runnable stages: the server ends the old attempt and claims the next stage for the same runner in the transaction that accepts the result, with a new attempt, lease and fencing. Capacity is released only on an explicit wait (input, external, dependency, retry backoff), stop or cancel, terminal close, or recovered lease expiry, and each release records its reason. Never waives checks, trust, permissions, fencing or cancellation | "Keep working until you really can't anymore." PRs #134-#139 waited 2-2.6 h queued at `self_review` after development while slots went to new development | Caleb |
| 64 | Dispatch (stage continuation) | A continuation is the runner's opt-in offer (fresh lease plus runnable stages) on the result request, not a server assumption. It honors dispatch pause, runner affinity and runner capacity like a claim, and the Captain loop omits worker stages from the offer while any project mapping is blocked. Plain `attended prepare` callers make no offer, so their items are requeued as before | The server can't know which stages a runner can launch next, and keeping the offer in the replayable request lets a retried submission return the same continuation. Pause stops all new stage starts, so it stops continuations too | Captain |
| 65 | Captain relay liveness | A runtime's session tools run only inside an agent turn, so the loop cannot wake the relay. Muster setup includes a standing serve: a dedicated relay chat serves continuously and the runtime's scheduler re-wakes it (README runtime mapping). When no server has polled or answered for 180 s while a request waits, the loop reports `relay_stalled`, adds the reason to each relay-dependent item's lease renewal so the board shows it, and runs the optional `notify_command`; the first poll clears it and notifies again. The stall clock starts at the first request after the last server poll, so expiry and requeue never reset it. 180 s is a `CaptainLoop` default, not a setting | Makes a stopped relay visible and self-healing without encoding a runtime in the core; generous to suit loaded machines (decision 56) | Captain |
| 66 | Local check timeouts | A local check that times out with no `FAIL:`/`ERROR:`/traceback or F/E markers in its output retries `pre_pr_validation` twice (60 s, then 120 s) before returning to `development`; a timeout with identified failures returns immediately. The runner runs at most `local_check_capacity` (default 1) local check sets per host; the rest wait as external gate `local_check_capacity` without using their timeout | A pure timeout is ambiguous between a hung test and host contention (PH-V1a v33 timed out after 1800 s with five workers on one machine); bounding contention fixes the cause, and bounded retries keep real hangs visible | Captain |
| 67 | Simplicity over compatibility | Don't add database migrations, legacy-schema support or backwards-compatibility machinery unless explicitly requested. Change schemas, APIs and formats directly and update callers. Doesn't permit deleting or resetting live data | "Record this in the principles -- do not worry about database migrations or backwards compatibility for now, especially we are still proving this out. Mark this in the Agents.md. Let's focus more on simplicity for now." Then, for #153: "remove the \"while the prototype is being proved out\" notation. Just make it unqualified for now to not do this migration stuff" | Caleb |
| 68 | Coordination, not a gate | Phalanx adds visibility and coordination and must not become an extra permission gate between the agent runtime and useful work. The remaining gates are repository and GitHub rules, trust and credentials. Phalanx records, reconciles and flags, and never blocks starting work. Merging the Captain and relay chats alone doesn't fix reliability. Proposed design: [direct-sessions.md](direct-sessions.md) | "Phalanx should add visibility and coordination, not become an extra permission gate between Copilot and useful work." The serial relay, relay SQLite contention, the shared slot cap and merged PRs never reaching delivered were the bottlenecks | Caleb |
| 69 | Sources of truth | The Phalanx server and GitHub together are the source of truth. GitHub owns PR existence and state, heads, checks, reviews, merges and deployments. Chat memory, handoff notes and local files are never authoritative. No runner-local state database: the local SQLite stores are to be removed | "Source of truth should always be a combination of phalanx server and github itself (pr state, etc)"; "I DO want to get rid of the local sqllite db. | 70 | Captains | Several Captains may run at once. Captains only coordinate and never do item work, so safety is per item: atomic writer registration with exactly one writer per execution. Shift bounds and the keeper that starts a Captain when none is alive are D7 and D8 in [direct-sessions.md](direct-sessions.md) (decision 71) | "Multiple captains is fine. | 71 | Direct sessions (D1–D8) | Accepts the defaults in [direct-sessions.md](direct-sessions.md#decisions). D1: workers push and open their PRs under repository rules. Takes effect as the migration steps land; AGENTS.md is updated at step 5 | Caleb accepted all proposed defaults D1–D8 (relayed by the Captain, 2026-11-23) | Caleb |
| 72 | Muster locator | `muster start` and `muster status` find the muster from `--home`, then `PHALANX_HOME` (absolute), then the one per-user file `~/.phalanx/muster.json` holding exactly `{"home": "<absolute path>"}`, written by `muster use DIR`.

# Phalanx decisions

These are design calls for Phalanx. Most are best guesses the Captain made without asking Caleb; Caleb reviews them and may override any one. The **Decided by** column separates the two:

- **Caleb**: Caleb made the call explicitly. Agents don't change it without asking him.
- **Captain**: an agent's best guess, open to Caleb's override.
- **Captain; confirmed, approved or amended by Caleb**: the agent proposed it and Caleb explicitly accepted or changed it.

Mark a row Caleb only for his explicit decision. To override, edit the row, set Decided by to Caleb and note the change. The Captain appends new decisions as it makes them. Worker questions it answers are also recorded on the item as `answered_by: captain`.

**Historical mechanisms:** PH-DS5 has removed the prior transport, scheduler, reservation,
PR-stage executor and client SQLite journal implementations. Earlier rows remain as decision
history, not operating instructions.
Both removals shipped in [#209](https://github.com/caltseng/phalanx/pull/209) and
[#214](https://github.com/caltseng/phalanx/pull/214); the standalone API/Scribe server
was not the relay and remains. Use the [implementation map](architecture.md) for
current code ownership. Rows recording a proposal or a pilot snapshot are not proof
that a feature is implemented or deployed.
Row 63's execution-continuity principle now uses one registered writer across fenced stages.
Rows 68-71 and [direct sessions](direct-sessions.md) describe the running architecture.
Earlier validation/promotion/check-in rows describe retired stages unless explicitly marked
direct; there is no second runnable execution path.
In particular, direct draft-only publication follows its explicit ceiling rather than
the old promotion path, and direct targets/auto-merge follow rows 81/85/86, as amended by
row 93's pre-activation review/check ordering, rather than a
global runner setting. Row 71 records the original defaults: the persisted dispatch
`max_writers` setting now enforces the workspace concurrent-writer budget at registration,
and a scoped writer credential spans separately fenced attempts, not just one attempt.
Row 59's local-read allowlist now also covers Captain and flag reads for the direct
board. Caleb's local-dashboard amendment (2026-11-24: "If the dashboard is local only,
we shouldn't need to put a token in") additionally authorizes narrowly wired
`/operator/api/` actions with explicit local-board mode, a direct loopback peer, local Host
and same-origin writes. Forwarding headers and untrusted/null origins cannot grant local
authority; `/v1` write authorization stays unchanged. The service owner verifies the
loopback-only listener and explicit configuration before rollout; review/merge is not deployment.

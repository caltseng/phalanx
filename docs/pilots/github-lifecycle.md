# PH-02 · GitHub lifecycle field report

GitHub exposes enough state for PH-13 to publish and recover a draft and for PH-14 to gate and verify promotion. Use Git for revision-conditional branch publication, REST for PR reads and writes, and GraphQL for ready promotion. The key limits are the lack of a head precondition on creation and promotion, and the lack of a base precondition on the ordinary merge call.

This report combines documented contracts with read-only inspection of [Phalanx PR #1](https://github.com/caltseng/phalanx/pull/1). The implementation choices below apply to the first runner adapter. The [design spec](../../SPEC.md) and [state machine](../../STATE_MACHINE.md) govern transitions.

## PH-13 publication and recovery

| Operation | Provider contract and runner behavior |
| --- | --- |
| Publish the topic ref | Use an item-specific branch and push the immutable candidate SHA explicitly to its full remote ref. Use `--force-with-lease=<ref>:<expected>` with the previously recorded remote SHA, or an empty expectation for initial creation. Require the recorded old SHA to be an ancestor of the new candidate for ordinary updates. The explicit lease can authorize a rewrite, so the ancestry check is separate. Read back the exact ref after a success or interruption. [Git push](https://git-scm.com/docs/git-push) |
| Create the draft | Use `POST /repos/{owner}/{repo}/pulls` with `head`, `base`, `title`, `body`, and `draft: true`. Creation selects refs by name. Read the ref before sending and verify the returned PR by number after sending, including its head repository/ref/SHA, base repository/ref, open state and draft flag. Save the REST number and GraphQL node ID. Compose the description with one attribution footer before sending. [Create a PR](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request) |
| Recover a lost create response | Search the base repo's PR list by exact owner/head and base, including closed PRs, and verify identity with a fresh PR read. Also inspect results for the same head without the base filter to catch an externally retargeted PR. Use a bounded, paginated lookup with backoff. Reuse a matching result. After successful reads yield no match within the bound, retry creation. On an existing-PR validation error, look up the PR again. Keep a recorded primary stable. During initial adoption, prefer the known response ID, or pick the lowest PR number among verified equivalent matches and surface the others. A different head, closed PR, or retargeted PR requires reconciliation. [List PRs](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests) |
| Update an existing PR | Push the revised candidate to the same topic ref with the same lease rules. The PR follows that branch. Preserve any existing ready state. Keep metadata writes out of ordinary retries. The REST metadata update can retarget the base and has no documented revision precondition. GitHub's separate update-branch operation merges the base into the topic asynchronously, accepts `expected_head_sha`, and returns `202` on acceptance or `422` for a head mismatch. V1 can prepare the changes locally and publish a known SHA directly. [Update a PR](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request) · [Update a PR branch](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request-branch) |

Before a write, persist its intent with item and attempt IDs, state version, operation, repo and ref identities, expected remote head and observed base tip when relevant, desired candidate SHA, and PR ID when known. Confirm the current claim immediately before the call. Serialize conflicting writes for the item on the runner and keep a sent or uncertain intent visible until reconciled. An expired claim stops the old attempt from advancing server state. GitHub does not receive that claim, so a successor must account for a prior in-flight write before it submits a conflicting one.

For a lost push response, inspect the remote ref. At the desired SHA, adopt the effect under the current claim. At the recorded old SHA or expected absence, retry the same conditional write after accounting for the prior writer. Any other value routes to reconciliation. Keep the original lease expectation through retries rather than silently replacing it with a fresh remote value.

### Runner integration

`DraftPublisher.publish` handles first draft publication on one device. Build the intent from the server's registered repository, item and base, the runner's expected remote revisions, and the candidate verified from PH-11 worker handoff. An optional worker PR number or URL is not publication evidence. Share one runner-owned journal directory across local processes. It contains the intent, latest attempt and state version, pending operation, and known or verified PR number. The per-item lock serializes the local calls, including recovery. A process that loses its claim leaves the journal available to a successor with the same intent.

The attended runner still needs to supply the current-claim callback for the intended publication stage and commit the outcome with a server-side claim and state-version check. A verified result supplies the exact primary PR and any duplicate candidates. Conflicts can include exact provider observations for reconciliation. Map pending and lost-claim outcomes to recovery, and use the base-changed outcome to request a revised candidate when there is no unresolved write. A confirmed push without a sent draft can be superseded by a candidate whose lease expects the recorded pushed commit. A different intent stays blocked while a push or draft write is unresolved. The journal is local recovery state. The API remains authoritative for stage, evidence, and operator visibility.

## PH-14 validation and promotion

| Point in the lifecycle | Evidence needed |
| --- | --- |
| Before upload when feasible, and before first promotion | Local or live checks identified by repo instructions. Bind results to the candidate SHA and include commands and outcomes or a documented bypass allowed by repo policy. The first draft can exist while formal pre-validation runs. |
| On the draft candidate | Verify the PR points to the validated SHA. Wait for repo-configured draft-only checks and push-dependent previews that must pass before promotion. Run any required preview smoke test against the verified deployment. |
| After promotion or an update to a ready PR | Verify required GitHub checks, other expected CI, and any ready-stage preview for the current revision. Keep independent review and the check-in gate separate from this observation. |

Call GraphQL `markPullRequestReadyForReview` with the PR node ID. Its input supports `clientMutationId` for correlation and has no expected head or base. Read identity, state, head and base immediately before and after. If the response is lost, reread the PR. A ready PR on the expected revision satisfies promotion regardless of who acted. Retry only after reconciling a still-draft PR on the expected revision. Route unexpected changes to reconciliation. A head change during the call can leave an unvalidated revision publicly ready and trigger review or CI. Record the side effect, revalidate, and avoid automatically converting the PR back to draft. [GitHub GraphQL PR schema](https://docs.github.com/en/graphql/reference/pulls#markpullrequestreadyforreview)

- Use repository expectations together with active rules for the target branch and classic protection where visible. Read paginated check runs and commit statuses by SHA, matching configured check name and expected source app where applicable. A required check and status with the same name both need to pass. GitHub can use the test merge commit when it has status results, so correlate the candidate check SHA with the current PR head and base. The open PR's computed merge commit SHA can be unavailable during computation. Recheck before accepting results from that commit. A single aggregate status cannot establish which required checks actually ran. [Branch rules](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch) · [Classic protection](https://docs.github.com/en/rest/branches/branch-protection) · [Required checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks) · [Check runs](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) · [Commit statuses](https://docs.github.com/en/rest/commits/statuses)
- GitHub permits successful, skipped, and neutral required status checks under branch protection. Apply any stricter repo gate that requires actual execution. Count an absent expected check as waiting, with a scheduled recheck and a visible reason. Surface persistent absence or denied policy reads as an actionable blocker when needed to verify a gate. A confirmed empty set of required and expected checks can advance. [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)
- Resolve a preview by configured provider, environment and revision. For GitHub Deployments, look up the deployment by candidate SHA and environment and read its latest status and environment URL. For an integration using check runs or statuses, match its configured source and revision before accepting the URL. Store deployment or run ID, SHA, URL and validation result. A branch alias can serve a different revision by the time a smoke test runs. Use an immutable deployment URL or confirm the served revision. [Deployments](https://docs.github.com/en/rest/deployments/deployments#list-deployments) · [Deployment statuses](https://docs.github.com/en/rest/deployments/statuses)
- Verify the actual repo workflow triggers. GitHub Actions runs `pull_request` by default on `opened`, `synchronize`, and `reopened`. A workflow that only runs on ready PRs may need `ready_for_review` to run after promotion without a new push. Draft-only jobs and preview providers depend on repo and integration configuration. Test pending, missing, and failure separately. [Actions events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

## Check-in and outside changes

For ordinary direct check-in, verify the primary PR is open and ready. Recheck item authorization, target ref and current tip, head SHA, required checks and deployments, review and conversation requirements, and the allowed merge method. Read the target ref directly for the current tip. Use a credential subject to repository policy. Use `PUT /repos/{owner}/{repo}/pulls/{number}/merge` with the verified `sha` and chosen `merge_method`. A stale head produces `409`. The endpoint has no expected-base parameter. A fresh read reduces that race, and GitHub's applicable branch rules still enforce their own gates. If the repo or item requires atomically merging against an exact base SHA, surface the unsupported guarantee and wait for an approved path. A required merge queue needs its own enqueue and eventual-merge verification path, so leave queue-required check-in waiting in the direct-merge adapter. [Merge a PR](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) · [Merge queues](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

After a merge response or interruption, read the primary PR. Verify merged state, PR and revision identity, target and the method-appropriate resulting SHA. For a merge commit, parent history can corroborate the candidate and show the immediate base at merge. Squash and rebase change commit identity, so candidate ancestry alone is insufficient. Correlate the provider's merged PR and resulting commit with the recorded candidate and intent. The merge-status endpoint can corroborate merged state but cannot establish candidate identity. If evidence is contradictory or the observed merge differs from intent, preserve it for disposition. Retry only after reconciliation confirms an eligible unmerged PR and the gates are still current. [Get a PR](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request) · [Check if a PR has been merged](https://docs.github.com/en/rest/pulls/pulls#check-if-a-pull-request-has-been-merged)

- **Outside topic push or deletion.** Fetch and compare with the recorded remote SHA. Preserve the outside change. Reconcile scope and revalidate the new candidate, returning through review as required. A deleted published ref warrants reconciliation before republication.
- **Base tip advance.** Re-read the tip and recompute the merge candidate and effective diff. Refresh evidence tied to the old base or merge candidate. If the repo requires the topic to be current or the diff is no longer valid, update locally and repeat validation for the resulting candidate.
- **Base retarget.** Treat a changed base repository or ref as an identity change. Reconcile the target against the item's authorization before another write.

## Observations and remaining verification

Read-only REST requests for [PR #1](https://github.com/caltseng/phalanx/pull/1) showed `state=closed`, `draft=false`, `merged=true`, and merge SHA `9800e4e6c7d870f5a95772a3353e95c5f0cad077`. The merge-status endpoint returned `204`. Local Git showed that merge commit's parents were the PR's recorded base `cbdca76c09ba342a73401cbb1f48f7c501c37f12` and head `b283c6d3e27757ba73980daf8ed9418ebd0945b2`. The head returned zero check runs and zero commit statuses, with a combined commit status of `pending`. This is evidence for decoding the empty-status case and for verifying a completed merge with parents.

The report's own PR provides a draft creation and read-back smoke test. Live promotion, check and preview triggering with real integration credentials, lost responses, outside head or base changes during a write, and enforced merge rejection remain pilot cases. Test PH-13 with a remote ref advanced between observation and push, a create response lost after success, and a paused writer whose lease expires. Test PH-14 with draft and ready triggers, a preview URL serving the wrong revision, an absent expected check, and a head change during promotion. Record which gates the target repo's actual credential can read and which policy GitHub enforces at merge. This pilot scope leaves live end-to-end check-in and merge queue behavior unverified.
